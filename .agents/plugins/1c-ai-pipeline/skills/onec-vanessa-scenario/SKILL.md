# Сценарии Vanessa Automation

Используй навык, когда результат задачи доказывается сценарием Vanessa Automation: открытие форм, действия пользователя, печатные формы, подготовка эталонных данных перед прогоном.

Навык описывает предметную методику фич. Запуск и наблюдение выполняет MCP Runner; его навык описывает параметры и квитанции.

## Перед первой записью feature

Сначала найди общие модули через `list_modules` и прочитай подходящий код через
`read_module_source`: проект может уже содержать подготовку контрольных данных и
экспортные функции проверки. Используй подтверждённые функции вместо сочинения
API создания объектов. Отсутствие прочитанного кода — повод исследовать, а не
угадывать названия методов.

Проверка расхождения не должна создавать дополнительный документ на величину
расхождения. Документы должны отражать заявленные исходные условия. Ожидаемое
значение — по документам; ошибочное значение отчёта не становится эталоном.
Неизвестный шаг или ошибка BSL в JUnit означает неготовый сценарий: исправь его
и повтори запуск, пока проверка не дойдёт до сравнения предметных значений.

## Сначала отличи проверку от подготовки

- Сценарий проверки — файл `.feature`. Модуль BSL его не заменяет.
- Подготовка базы и проверка — разные фичи. Подготовка отбирается тегом из её файла настроек; не выдумывай тег, которого в проекте нет.
- В JSON имя тега без `@`, в фиче — с `@`. Если у подготовки и основного прогона разные файлы настроек, их списки тегов не смешивай.

## Пиши фичу шагами проекта

- Файлы лежат в `features/**/*.feature`, в корне или в каталоге вроде `Экспортные сценарии/`. Это Gherkin на русском. Фичи OneScript с `# language: ru` — это 1bdd, не Vanessa.
- Первая строка: `# language: ru` или `#language: ru`. Заголовок — `Функционал:` или `Функциональность:`. `@tree` частый; если в настройках включён тег дерева по умолчанию, иерархия работает и без него.
- Текст шага бери из соседних фич этого проекта. Не придумывай формулировку, которой в проекте нет. Новую формулировку добавляй только вместе с реализацией шага.
- Клиента подключай шагом из соседних фич: уже существующий TestClient или именной клиент с логином и паролем.
- Библиотека экспортных сценариев помечена `@ExportScenarios` (сравнение тега без учёта регистра). Имя сценария — вызываемый шаг; параметр в заголовке в кавычках, в теле — в квадратных скобках. На такую библиотеку часто вешают `@IgnoreOnCIMainBuild`: это не сценарий проверки.
- В приёмке пользовательского интерфейса не подменяй действия пользователя выполнением кода встроенного языка. В подготовке код на сервере допустим только когда шага недостаточно: окно ИТС, классификатор поставки, запись, которую подписка пускает лишь в режиме загрузки. Если в проекте уже есть свой экспортный шаг записи константы, вызывай его.

## Данные и печатные формы

- Скалярные константы и эталонные справочники загружай шагами генератора тестовых данных Vanessa: перезаполнение константы и проверка или создание объектов справочника. Источник значений — файл рядом с фичами, не модуль.
- Ссылочные константы ставь после справочников, на которые они смотрят.
- Печатную форму не считают проверенной тем, что её открыли. После формирования сравни Табличный документ с эталоном `.mxl` рядом с фичей шагом вида `Табличный документ "ИмяРеквизита" равен макету "Эталон.mxl"`. Имя реквизита бери с формы печати. Эталон не собирай кодом и не набирай таблицей внутри шага вместо файла.
- Заголовок окна в шаге «открылось окно» бери с формы, а не выдумывай.

## Доказательство

- Каталог фич в настройках бывает каталогом или одним файлом. Выгрузка формы часто вложена; булево пишут `true` или строкой `Истина`.
- Одна информационная база — один владелец прогона. Независимые прогоны идут по очереди. Для проверки конкурентности нужны несколько согласованных сеансов внутри одного прогона: общий набор тестовых данных, управляемое пересечение операций и результаты каждого сеанса. Возможность такого исполнения подтвердить у штатного инструмента; два последовательных действия гонку не проверяют. Живое окно после сценария само по себе не определяет итог: проверяй квитанцию и владение процессом. Не запускай независимый прогон поверх незавершённого и не завершай чужие сеансы.
- Запуск и наблюдение выполняет vanessa-runner. Не подменяй его прямым CLI и не объявляй успех по наличию EPF без квитанции прогона.

## Обращение о видимом отчёте

Слова пользователя «отчёт показывает» задают объект проверки — сформированный
отчёт в клиенте 1С. Найденная серверная функция помогает объяснить механизм,
но её вызов не воспроизводит обращение. Читай модуль формы, её команды и тип
реквизита результата. Если формы нет, зафиксируй неполноту стенда; не меняй
критерий приёмки на проверку функции.

До запуска сверь feature с цепочкой: подключение TestClient → открытие формы →
формирование → проверка видимого результата. Каждому действию соответствует
реальный шаг установленной библиотеки. Имена формы, команды и реквизита бери
из проекта; ожидаемые строки — из исходных условий и документов.

Где найти определения в стандартной Vanessa Automation:

- `features/Libraries/TestClients/step_definitions/РаботаСTestClient/Forms/Форма/Ext/Form/Module.bsl`:
  `Когда я подключаю клиент тестирования с параметрами:`. Затем отдельной
  таблицей колонки `Имя`, `Тип клиента`, `Порт`, `Строка соединения` и значения
  разрешённой среды. Это запуск TestClient, а не просто текстовое имя базы.
- `features/Libraries/VB/step_definitions/ОткрытьФормуЧерезКоманду/Forms/Форма/Ext/Form/Module.bsl`:
  `Дано я открываю основную форму отчета "<имя отчёта в метаданных>"`
  либо `Дано я открываю навигационную ссылку "<ссылка>"`.
  Для отчёта навигационная ссылка имеет вид `e1cib/app/Отчет.<Имя>`,
  а путь модуля EDT навигационной ссылкой не является.
- `features/Libraries/UITestRunner/step_definitions/РаботаСИнтерфейсом/Forms/Форма/Ext/Form/Module.bsl`:
  `И я нажимаю на кнопку "<кнопка>"` и
  `И табличный документ "<реквизит>" содержит строки:` с таблицей ожидаемых
  заголовков и строк. Для реквизита типа таблицы используй шаг таблицы,
  а не табличного документа.

Пути выше — указатели на определения, не разрешение угадывать параметры.
Прочитай определения шагов и примеры перед записью feature. Проверь, что их
каталоги включены в настройки загрузки библиотек. При неизвестном шаге найди
его точное определение и исправь текст; удаление подключения или формирования
не исправляет сценарий.

Новые результаты хранятся в каталоге текущего прогона. Сохраняй исходный
JUnit/Allure, различая ошибку шага и несовпадение видимых данных. Если нужен
снимок экрана для разбора, сохраняй сформированный отчёт; код шага и текст
чата не являются изображением отчёта.

## Воспроизведение серверной логики

Это отдельный вид диагностики, когда предмет задачи — серверная функция или
запрос. Такой прогон не проверяет экран и не заменяет воспроизведение
обращения о пользовательском отчёте. В UI-сценарии серверный код допустим для подготовки данных и проверки
состояния регистров после пользовательского действия. Он не заменяет само
действие в форме. Прочитай подходящие модули проекта до записи проверки.

Определения шагов находятся в
`features/Libraries/ВстроенныйЯзык/ВстроенныйЯзык/Forms/Форма/Ext/Form/Module.bsl`.
Многострочный блок начинается на **следующей строке** после текста шага:

```gherkin
И я выполняю код встроенного языка на сервере
    """bsl
    // Проверенный код подготовки из проекта
    """
```

Не добавляй `"""bsl` в строку шага и не смешивай блок кода с таблицей Gherkin.
Используй подтверждённые методы проекта вместо сочинения API. Не создавай
дополнительные документы ради получения желаемой разницы и не меняй ожидаемое
значение ради зелёного результата.

## Приемка последовательностей и достоверность результата

`Выборка.Следующий()` возвращает булево, а не количество записей. После перехода
читай поле агрегата `Выборка.Количество`. Сравнение двух значений `Истина`
не проверяет отсутствие дублей. Проверяй ожидаемое число записей и их сумму,
а для неизменного вида учета — состав проводок, границу и дату запрета до/после.
Повторный вызов восстановления должен сохранить число и состав проводок.

Дата BSL задается `Дата(год, месяц, день, часы, минуты, секунды)`; не передавай
произвольную строку вместо даты. Строку соединения бери из окружения без
перепечатывания. До запуска сверь каждый шаг с реальным определением библиотеки.

Перед выводом «проверено» прочитай конечный JUnit/Allure именно своего runId.
`task_result` без ошибки, завершенный процесс или уверенность в исходниках
не доказывают успех. При ошибке шага не перечисляй ожидаемые проверки как
выполненные. Укажи конкретную ошибку и фактически пройденную часть.

## Действие в форме и проверка учета

Для приемки учетной команды раздели три части: исходное состояние → команда
формы через TestClient → проверка проводок и границ. Снимай исходные записи
до действия; сравнивай одинаковые поля в устойчивом порядке после него.
Сумма без состава записей не доказывает сохранность учета: две ошибки могут
взаимно компенсироваться. В отрицательной проверке подтверждай ожидаемый
текст или код отказа, а не любое исключение.

Отчет о прогоне должен соответствовать проверенному feature и конкретному
runId. Не заменяй исходный упавший отчет успешным: храни результаты разных запусков
раздельно и показывай отчет принятого запуска.

После принятого прогона используй его отчет и уже сформированную форму.
Снимок экрана не требует повторного изменения данных. Если для съемки форму
нужно открыть заново, выполни только открытие формы без повторного заполнения
базы.
