# Модульные тесты YAxUnit

Используй навык, когда результат доказывается модульным тестом YAxUnit: логика общих модулей, объектов, менеджеров — без клиентского UI.

Навык описывает, как писать и регистрировать тесты. Поиск конфигурации запуска, прогон, отладка и отмена — навык edt-mcp-project-yaxunit и инструменты edt-mcp. Сценарии Vanessa — отдельный навык onec-vanessa-scenario.

## Где живут тесты

- Тесты — в общем модуле **тестового расширения**. Движок YAxUnit и расширение с тестами загружены в информационную базу до прогона; безопасный режим расширения выключен.
- Каталог вроде `tests/cfe/<имя>` — удобное место хранения. Имя расширения бери из метаданных: в EDT — `src/Configuration/Configuration.mdo`, в выгрузке конфигуратора — `Configuration.xml`. Не из имени каталога.
- Движок обычно лежит отдельно (часто `tests/cfe/YAXUNIT`). Если каталог с тем же именем расширения уже есть, обновляй его, а не создавай второй.

## Регистрация и тело теста

- Модуль регистрирует тесты в экспортной процедуре `ИсполняемыеСценарии` через `ЮТТесты.ДобавитьТест(...)`. В этой процедуре тестовые данные не создают.
- `ДобавитьТест(ИмяТестовогоМетода, ПредставлениеТеста = "", ТегиСтрокой = "", Контексты = Неопределено)`. Имя совпадает с экспортной процедурой теста. Теги в строке — через запятую. Без четвёртого аргумента тест идёт во все контексты модуля; серверный тест ограничивай строкой `"Сервер"`.
- Утверждения: `ЮТест.ОжидаетЧто(Значение)` и цепочка с новой строки — `.Равно()`, `.ИмеетТип()`, `.ИмеетДлину()`, `.Содержит()` и другие методы движка, подтверждённые для версии проекта.
- `УдалениеТестовыхДанных()` удаляет только объекты, созданные через `ЮТест.Данные()`. Иначе данные после теста не считай автоматически убранными.
- Транзакция у движка по умолчанию выключена. Включай `.ВТранзакции()` при регистрации или настройкой `ВТранзакции` в конфиге прогона. Флаг действует на сервере и на толстом клиенте.

## Конфиг прогона

- В `tools/yaxunit.json` (или эквиваленте проекта) держи `closeAfterTests: true`, иначе окно 1С не закроется. `filter.extensions` — имя расширения из метаданных, не имя каталога.
- Если прогон передаёт свой фильтр модуля или метода, список в json его не заменяет: для узкого отбора задай фильтр в вызове edt-mcp (`modules` / `tests=Модуль.Метод`).
- Одна информационная база — один владелец прогона. Независимые прогоны не пересекаются. Проверка конкурентности может использовать несколько согласованных сеансов внутри одного прогона, только если штатный исполнитель поддерживает такой сценарий. Последовательные вызовы и моки не доказывают отсутствие гонки. Завершение определяй по квитанции и владению процессами, а не только по открытому окну; чужие сеансы не завершай.

## Доказательство

- Сначала убедись, что движок и тестовое расширение есть в проекте EDT и в базе. Если движка нет, остановись: установка — отдельное решение владельца стенда, этот навык её не подменяет.
- Напиши или измени тест, зарегистрируй метод, затем запусти через edt-mcp-project-yaxunit на авторизованном тестовом приложении. Успех — квитанция прогона с выполненным задуманным тестом, не наличие файла модуля.

## Тесты рядом с новой функциональностью

В кейсе развития главный результат — новое действие бизнес-роли. Модульный тест подтверждает нужную логику и сохранность прежнего поведения; он не заменяет карточку, команду или рабочее место. Служебные подсистемы YAxUnit и генерации кода исключай из основного командного интерфейса прикладного решения, сохраняя движок активным. Наличие установленного YAxUnit не означает, что конкретный тест был выполнен: сообщай фактический способ подтверждения.
