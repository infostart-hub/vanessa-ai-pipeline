# Диалоги безопасности 1С, лицензия разработчика и доверие тестовых баз

## Различение причин остановки клиента

Если клиент остановился на диалоговом окне, сначала установи точную причину по журналу регистрации 1С (`1Cv8Log/*.lgp`) и статусу запуска (`enterprise_status`, в т.ч. классификатор `unsafe_action_protection`), не запуская поверх него второй экземпляр:

1. **Защита от опасных действий (`DisableUnsafeActionProtection`)** при открытии внешней обработки `.epf` или подключении внешней компоненты;
2. **Информационное предупреждение учебной/разработческой лицензии**;
3. **Отсутствующий файл поставки, неверный путь `VAParams` или прикладное исключение BSL при старте**.

Ключ командной строки `/DisableStartupDialogs` подавляет пакетные стартовые сообщения, но **не** нажимает автоматически «Да/ОК» на предупреждениях безопасности и не должен передаваться интерактивному `TestClient`, если это мешает штатному сценарию (`ENTERPRISE` не наследует этот ключ от `DESIGNER`).

## Подтверждение предупреждений на Windows (`enterprise_authorize` и лицензия разработчика)

- **Предупреждение лицензии разработчика (Windows)**: управляемый запуск `test vanessa` поддерживает явный флаг `--acknowledge-developer-license`. Помощник проверяет принадлежность окна собственному Job Object, PID, время создания процесса и точный текст предупреждения, после чего отправляет штатное закрытие только этому окну (квитанции отражаются в `developerLicenseNotices`).
- **Интерактивное разрешение операции безопасности на Windows (`enterprise_authorize`)**:
  - вызывай `enterprise_authorize(runId, capability)` строго для собственного запуска и конкретной разрешённой возможности (`open_processing` или `administer_users`);
  - учитывай двухшаговое поведение платформы 1С: после первого подтверждения (`state: requested`) 1С часто прерывает исходный вызов и показывает второе информационное окно *«Текущее выполнение действия было прервано для выдачи предупреждения... Просьба сейчас вызвать действие еще раз»*. В этом случае повторно вызови `enterprise_authorize` для того же `capability` (`state: acknowledgement_requested`, `interruptedAction: true`, `requiresActionRetry: true`), после чего заново запусти прерванное действие;
  - на **macOS** не вызывай Windows-специфичный `enterprise_authorize` и не пытайся закликивать окно средствами рабочего стола — используй предварительную настройку доверия тестовой базы в `conf.cfg`.

## Штатная настройка доверия тестовой базы (`conf.cfg`) на Windows и macOS

Для безоператорных прогонов на выделенных тестовых базах (при явном согласии пользователя на конкретные базы; уже полученное согласие на этот набор тестовых баз повторно запрашивать не нужно):

1. Параметр `DisableUnsafeActionProtection` в `conf.cfg` (`%LOCALAPPDATA%/1C/1cv8/conf/conf.cfg` на Windows, `~/.1cv8/1C/1cv8/conf/conf.cfg` на macOS) задаёт список POSIX Basic Regular Expressions через `;`, сопоставляемых со строкой подключения ИБ.
2. В поставке Runner предусмотрен идемпотентный скрипт `tools/macos-trusted-infobases.py --infobase /absolute/path/to/test-ib` (при необходимости `--config <path>`):
   - вызов **без `--apply`** показывает предварительный план изменений;
   - применение выполняется с `--apply --acknowledge-trust-change`, отзыв при удалении стенда — с `--revoke --apply --acknowledge-trust-change`.
3. **Правила безопасности при правке `conf.cfg`**:
   - сохраняй все существующие ключи и правила файла;
   - добавляй правило **только на точный путь или точное имя** согласованной тестовой базы (с учётом регистра, обратных слешей на Windows и закрывающей кавычки/слеша, чтобы правило не совпало с соседней базой);
   - **категорически запрещено** подставлять общие шаблоны вроде `.` или `.*` или менять настройки продуктивных/пользовательских баз без явного поручения.
4. Изменение `conf.cfg` не влияет на уже висящий диалог открытого клиента: штатно заверши прежний запуск (`activeProcessCount: 0`) и выполни чистый прогон с новым `runId`, подтвердив результат свежим отчётом Vanessa.
