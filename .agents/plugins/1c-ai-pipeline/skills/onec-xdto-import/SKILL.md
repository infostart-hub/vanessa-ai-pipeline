# XML в прикладные данные 1С

Разделяй три результата: XML разобран по контракту; значения сопоставлены с предметными объектами; пользователь получил сохранённый прикладной документ. Первый результат не доказывает остальные.

## Входной контракт

Прочитай XSD и характерный XML полностью. Установи namespace, корневой элемент, типы, обязательность, кратность, единицы, идентификатор объекта и его версии. Для существующей загрузки сначала исследуй её пакет и код. Названия элементов не являются названиями справочников 1С. Отсутствующее значение, пустая строка и xsi:nil имеют разный смысл.

Без XSD можно подготовить явно обозначенный контракт по примеру, но один пример не доказывает полноту формата. Не объявляй произвольный XML валидным только потому, что ЧтениеXML прочитало его.

## Пакет в существующем EDT

Прочитай актуальные guides create_metadata, modify_metadata и get_metadata_details. Проверь существующие XDTOPackage и их targetNamespace. Создавай пакет, объектные типы, затем свойства и корневое свойство через поддерживаемые операции MCP. Для свойства установи точный тип, границы кратности и nillable. Namespace — часть идентичности типа; одноимённые типы разных пакетов не взаимозаменяемы. Не перезаписывай пакет с чужими изменениями.

Импортируемые пространства имён должны разрешаться в настоящие типы, а не незаметно становиться anyType. xs:include и xs:import не взаимозаменяемы: замена требует сохранения семантики пространства имён. Ограничения конкретного генератора не являются ограничениями платформы.

xs:choice, xs:all, вложенные группы, ключи/keyref и ограничения кратности могут требовать дополнительной проверки исходной XSD. Уплощение модели меняет допустимые данные. Если модель EDT не выражает условие, сохрани проверку этого условия отдельно; не принимай такое упрощение молча. Ошибка контракта должна оставлять прикладные данные без изменений.

## Предметное преобразование

Составь соответствие: поле XML → тип XDTO → реквизит 1С → преобразование. Ссылки находи по устойчивому внешнему ключу и согласованной области. Совпадение наименования само по себе не подтверждает соответствие. Не создавай неизвестные материалы, единицы, сотрудников или счета без предусмотренного правила.

Покажи предпросмотр: исходное значение, найденное соответствие, количество и единица, понятная причина незаписываемой строки. Раздели чтение и команду записи. Новый номер версии не должен незаметно переписывать уже используемую спецификацию или документ.

Повтор определяется бизнес-идентификатором источника и версией, а не именем файла. Одинаковый ключ и тот же состав дают ссылку на существующий результат; изменённый состав при том же ключе требует явного решения. Проверяй ключ повторно при записи и сохраняй согласованный объект целиком в одной транзакции. Для параллельных загрузок используй штатную блокировку области ключа.

## Прикладное выполнение

Используй штатную ФабрикаXDTO и сериализацию платформы; сигнатуры уточняй в документации текущей платформы. Ошибки преобразования не скрывай пустыми результатами. Файл пользователя должен быть доступен правильной стороне клиент-серверной границы: загрузи его во временное хранилище либо используй подтверждённый серверный путь в тестовом окружении.

Проверь на разрешённой базе: корректный документ создаётся и открывается; повтор не дублирует; неизвестное соответствие не создаёт частичный документ; несовместимый namespace или обязательное поле обнаружены до записи. Проверку конструкции пакета и чтение файлов не называй выполнением этого сценария.

Результат для аналитика: созданный документ, его версия и состав; понятный предпросмотр; при необходимости — место изменения кода. Показать только XML или таблицу типов недостаточно.
