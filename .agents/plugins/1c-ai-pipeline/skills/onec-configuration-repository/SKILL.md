# Хранилище конфигурации 1С и гибридный процесс с Git / EDT

Используй этот навык, когда проект конфигурации или расширения подключён к **Хранилищу конфигурации 1С** (напрямую в Конфигураторе, через пакетный CLI `1cv8 DESIGNER` или в гибридной связке с Git и 1С:EDT).

## 1. Главные инварианты безопасности

1. **Никогда не выполняй `/ConfigurationRepositoryUnbindCfg` без прямого письменного поручения человека.** Отключение рабочей базы от хранилища разрушает историю захватов и блокирует штатное помещение правок.
2. **Нулевой код возврата `1cv8` не доказывает успех операции с хранилищем.** Всегда передавай `/Out <лог> -NoTruncate` и проверяй текст лога на сообщения о блокировках, несовпадении версий, отсутствующих правах пользователя хранилища и ошибках объединения.
3. **Основная конфигурация и каждое расширение (`-Extension <Имя>`) имеют собственные независимые хранилища.** Не смешивай параметры подключения хранилища основной конфигурации и расширения.
4. **Не правь на диске незахваченные объекты в общей базе разработки.** Если объект не захвачен в хранилище до начала правок, параллельное помещение от другого разработчика приведёт к перезаписи чужого кода при полной загрузке.

## 2. Строгий протокол изменения объекта через Хранилище

При работе через файловую выгрузку (`DumpConfigToFiles` / `LoadConfigFromFiles`) соблюдай неизменную последовательность из 6 шагов:

1. **Актуализация базы из хранилища (`ConfigurationRepositoryUpdateCfg`)**:
   - Перед захватом обнови конфигурацию рабочей ИБ до актуальной ревизии хранилища, чтобы видеть последние версии связанных метаданных и сигнатур общих модулей.
2. **Захват целевых объектов (`ConfigurationRepositoryLockObjects`)**:
   - Захватывай минимально необходимый перечень объектов по точному списку (не захватывай всю конфигурацию рекурсивно без необходимости).
   - **Добавление нового объекта верхнего уровня** (новый справочник, документ, общий модуль, роль, подсистема) требует **захвата корня `Configuration`** (и затрагиваемых подсистем, если объект включается в их состав `Content`).
   - **Добавление вложенного элемента** (реквизита, табличной части, формы, макета, команды существующего объекта) требует захвата объекта-владельца (или конкретной подчинённой формы/макета, если меняется только она).
3. **Обязательная перевыгрузка захваченных объектов на диск (`DumpConfigToFiles -update` / частичная выгрузка)**:
   - Между прошлым обновлением Git-ветки и моментом захвата коллега мог поместить в хранилище новую версию этого же объекта. Если пропустить перевыгрузку после `LockObjects` и загрузить старый файл с диска, ты тихо сотрёшь чужие изменения!
4. **Внесение точечных изменений и проверка гигиены файлов**:
   - В выгрузке Конфигуратора сохраняй `UTF-8 с BOM` для `.bsl` в каталогах `Ext/`, не трогай вручную служебный `ConfigDumpInfo.xml` и бинарный `ParentConfigurations.bin`.
5. **Частичная загрузка и проверка (`LoadConfigFromFiles -files ...` / `-listFile ...` → `CheckConfig` / `UpdateDBCfg`)**:
   - Загружай только изменённые файлы, а не весь каталог конфигурации целиком.
   - Перед помещением в хранилище выполни синтаксический контроль и убедись, что конфигурация БД обновляется без потери данных и битых ссылок в ролях/подсистемах/подписках.
6. **Помещение в хранилище (`ConfigurationRepositoryCommitObjects`) с осмысленным комментарием**:
   - Передавай явный комментарий задачи/тикета и список помещаемых объектов. Если правка отменена — освободи объекты через `ConfigurationRepositoryUnlockObjects` с повторным обновлением конфигурации из хранилища.

## 3. Гибридный контур `Хранилище 1С ↔ Git ↔ 1С:EDT`

Во многих командах Хранилище 1С остаётся мастер-источником поставки, а Git и 1С:EDT используются для код-ревью, статического анализа и прогона тестов:

| Сценарий | Правило согласования |
|---|---|
| **Хранилище → Git (зеркалирование ревизий)** | Синхронизатор выгружает ревизии хранилища в служебную ветку (`storage-sync`) с автором и номером версии хранилища. Агент не редактирует ветку зеркала напрямую. |
| **Git / EDT → Хранилище (перенос одобренного PR)** | Конвертация `EDT ↔ XML Конфигуратора` (`ring edt workspace export` / импорт) может менять порядок узлов XML и форматирование. Переноси в хранилище только список реально затронутых задачей объектов, сверив diff модулей и реквизитов после экспорта. |
| **Конфликт `ConfigDumpInfo.xml`** | В Git-ветках файл `ConfigDumpInfo.xml` часто даёт конфликты слияния версий объектов. Не склеивай его вручную построчно: используй частичную загрузку по явному списку файлов (`-files` / `-listFile`) либо переформируй индекс штатной выгрузкой Конфигуратора. |
| **Объекты типовой конфигурации на поддержке** | Если объект находится на замке поставщика («Объект поставщика не редактируется»), захват в хранилище сам по себе не снимает правила поддержки. Сначала согласуй с архитектором перенос доработки в расширение (`CFE`) — см. [`onec-extension-change`](../onec-extension-change/SKILL.md). |

## 4. Типовые аварии и диагностика

- **«Объект уже захвачен пользователем ...»**: не пытайся обойти блокировку прямой правкой локальной ИБ. Сообщи имя захватившего пользователя из лога `/Out` и предложи дождаться помещения либо разделить точку расширения (подписка на событие, собственный общий модуль, расширение).
- **Сирота в составе подсистемы или роли после частичного помещения**: разработчик поместил новый справочник, но забыл захватить и поместить `Configuration` / `Subsystem` / `Role` (или наоборот — поместил ссылку в подсистеме без самого объекта). Всегда помещай объект и его регистрацию в `Configuration` / подсистемах / базовых ролях атомарным набором в одной ревизии хранилища.
- **Сброс кэша хранилища в рабочей ИБ**: при повреждении локального кэша хранилища в каталоге базы проверяй целостность через копию ИБ, не отвязывая боевую сборочную базу без резервной выгрузки `.cf` и списка захваченных объектов.
