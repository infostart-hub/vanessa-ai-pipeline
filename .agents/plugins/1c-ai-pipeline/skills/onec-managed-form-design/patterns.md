# Паттерны по пользовательской задаче

Эти варианты помогают выбрать композицию;
они не вводят универсальных обязательных запретов и не заменяют требования задачи.

## Документ

Сгруппировать идентификацию, участников и организационные данные по смыслу.
Рабочую область отдать табличным частям; итоги расположить рядом с их данными.
Дополнительные реквизиты отделять, когда это облегчает основной сценарий.
Не добавлять налог, договор или вторую таблицу, которых нет в модели и задаче.
Редактируемость итогов определяется бизнес-логикой, а не универсальным шаблоном.

## Обработка

Отделить параметры операции от рабочей таблицы и результата.
Выделить главное действие; дополнительные команды сгруппировать по назначению.
Команды сопоставить с обработчиками, доступностью и состоянием выполнения.
Модальность и блокировку владельца выбирать по сценарию, не по типу объекта.

## Список

Отборы связать с конкретными полями и настройками динамического списка.
Если фильтр включает отдельный флаг использования, определить состояния
«не применяется», «применяется», «пустое значение» и соответствующие проверки.
Реквизит списка, поля запроса и dataPath колонок должны быть согласованы.
Колонки только для просмотра и интерактивные колонки различать по сценарию.
Произвольный запрос передаётся validate_query в точном проекте; результат
валидации не доказывает полноту данных, ограничения доступа или скорость.

## Элемент справочника

Основные поля расположить первыми; код показывать, когда он нужен пользователю.
Сложную карточку разделить на смысловые группы, а не механически на две колонки.
Description/Code и программные имена брать из текущей модели, проверить
обязательность и доступность. Существующую форму не перестраивать ради шаблона.

## Мастер

Шаги разделять по действиям пользователя внутри формы.
Определить условия перехода, исправление ошибок, возврат и завершение.
Это поведение предметной формы; оно относится только к пользовательскому
сценарию внутри формы. Кнопки и блокировку интерфейса выбирать по сценариям задачи.

## Общие связи

Для таблицы: реквизит данных → колонка → путь → событие → обработчик.
Для действия: команда → кнопка → обработчик → изменение состояния.
Для предупреждения: конкретное состояние/ошибка → функциональное сообщение.
Декоративные баннеры и пояснения архитектуры в интерфейс не добавлять.
Имена элементов и групп следуют правилам текущего проекта; новые соглашения
не назначать обязательными без отдельного проектного решения.

## Автоматизированное рабочее место (АРМ)

Запрос на создание рабочего места не является сообщением об ошибке. Начать с роли,
ее рабочего дня и полезного результата: подготовить инструкции, выдать задания,
запустить подготовленные заказы. Не сводить АРМ к форме одного документа.

Составить карту участвующих объектов: документы-источники, справочники,
состояния и документы-результаты. Существующие объекты подтвердить в EDT;
новые создавать только в разрешенном объеме проектирования. Для каждого значения
указать владельца хранения; экранная копия и реквизит формы не заменяют запись.

Выбрать композицию: очередь с отборами → подробности выбранной записи → основные
действия → видимый результат. Определить пустую очередь, отсутствие выбора,
черновик, готовность, повтор команды и обновление данных после записи.
Сохранить переходы к исходным документам; не заставлять открывать их для каждого
обычного действия. Массовые действия вводить только с определенными правилами
частичного успеха, транзакций и сообщения о результате.

Проверить существующие картинки платформы и конфигурации. Переиспользовать
подходящие по смыслу; новые нужны, когда подходящих нет. Имя картинки проверить
в доступной версии, а не угадывать. Значки сопровождать подписями/подсказками;
цвет и пиктограмма не должны быть единственным признаком готовности.
Не подменять эргономику декоративными картинками: основная команда заметна,
данные сгруппированы по работе роли, таблицы и разделители изменяют размер.

Подтверждение результата: настоящий АРМ с несколькими связанными объектами,
запись и повторное чтение, переход роли к следующему действию. Проверку поведения
передать сценарию Vanessa; рисунок формы и статическая модель ее не доказывают.

Перед приемкой открыть АРМ в рабочем клиенте в целевом размере окна. Основная
очередь, выбранная запись и главное действие должны быть доступны вместе;
не отправлять результат работы роли за пределы экрана из-за растянутых полей.
Проверить ширину колонок, читаемость номеров, отсутствие бессмысленной прокрутки,
пустые состояния и видимый результат команды. Не показывать каждой роли все
реквизиты только потому, что они существуют в метаданных.
