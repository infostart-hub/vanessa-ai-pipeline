# Композиция управляемой формы

Вход: утверждённая задача, точный проект и форма, критерии приёмки.
Результат зависит от поручения: при анализе — предметное предложение и карта
изменений; при разрешенной разработке — примененная через EDT композиция формы
и проверенный пользовательский сценарий. Предложение не равно готовому АРМ.
Этот навык не утверждает задание и сам по себе не запускает 1С.
Явное поручение создать или доработать АРМ является разрешением на согласованные
изменения. Не требовать повторного подтверждения того же объема. Инструменты
записи выполняются через EDT MCP в пределах разрешённого объёма задачи.

1. Получить факты через существующий edt-mcp: list_projects,
   get_configuration_properties, get_metadata_details для объекта и формы.
   Обработчики исследовать через get_module_structure и read_method_source;
   modulePath подтвердить по проекту. Проект задавать явно. Схемы и
   get_tool_guide читать до вызова.
   Отсутствие инструмента зафиксировать явно; не переходить к ручной правке .mdo/.form/XML.
2. Для запроса на АРМ применить паттерн рабочего места из patterns.md: роль,
   несколько связанных объектов, очередь, действия и сохраненный результат.
   Не переопределять создание рабочего места как исправление дефекта.
   Установить сценарий: какие данные вводят, что выбирают, что вычисляют,
   какая команда завершает работу, какие ошибки пользователь должен исправить.
   Не додумывать поля, события и бизнес-логику из типового архетипа.
3. Выбрать композицию из [предметных паттернов](patterns.md). Сохранить принятую
   структуру продукта, если задача не требует её изменения. Двухколоночность,
   вкладки, модальность и имена групп — проектные решения, не стандарты 1С.
4. Для каждого нового или изменяемого элемента записать: назначение,
   владельца и родительскую группу; точный dataPath и тип; редактируемость;
   команду, событие, обработчик и контекст там, где они действительно нужны.
   Имена объектов брать из модели, а не из локализованных синонимов.
   Пустое имя события, отсутствующий тип или обработчик — неподтверждённая
   привязка; не заполнять пробел догадкой и не выдавать карту за полную.
5. Проверить привязки: существующий реквизит/колонка, команда и обработчик,
   допустимый контекст и отсутствие дублей. События из образца не создавать
   автоматически. Реквизит формы, реквизит объекта и видимый элемент различать.
   Для длинного строкового описания сначала проверить тип и ограничения
   реквизита, его `multiLine`/`extendedEdit` и свойства связанного поля ввода.
   Название `TextDocumentField` само по себе не доказывает пригодность для
   редактирования строки. Не менять вид элемента догадкой: подтвердить
   совместимость привязки и проверить сохранение значения после открытия формы.
   `InputField` также не означает однострочность: она зависит от свойств
   связанного реквизита и поля. Перед выводом о рассинхронизации модели и базы
   прочитать эти свойства; одного имени типа элемента недостаточно.
6. При разрешенной разработке выполнить согласованные изменения через
   существующий edt-mcp по точным целям. При запросе только на анализ вернуть
   предложение без записи. Поддержку конкретного свойства проверить по текущему guide
   create_metadata/modify_metadata. Не расширять согласованный объем изменений.
7. После изменения перечитать структуру через владельца EDT. Статическая
   модель доказывает структуру, но не расположение пикселей и не поведение.
   Если сериализованная форма пуста, исследовать ПриСозданииНаСервере и вызванные
   методы: элементы и команды могут создаваться программно. Не объявлять АРМ
   отсутствующим только по пустому дереву формы в EDT. Снимок дизайнера не
   выполняет серверный код; для такого АРМ нужен клиентский сценарий.
   Визуальное подтверждение и клиентский сценарий выполняются по критериям приёмки.

Материалы проекта хранить в своей операции хоста. Полноту явно ограничивать.
Для get_metadata_details учитывать секцию Errors даже при isError=false.
Формат FQN для других инструментов сверять отдельно: Form/Forms могут различаться.

get_form_layout_snapshot с formPath открывает и активирует редактор: вызов должен
входить в разрешённое действие. Его live guide различает nativeFormLayoutRender
и nativeFormBufferedLayoutRender. Нулевые bounds при native render не доказывают
пустоту формы и не исправляются повтором. Не менять flags и не перезапускать EDT
ради исследования. get_form_screenshot требует отдельной проверки доступности;
после изменения использовать refresh по актуальному контракту инструмента.


## Предметное предложение

Указать проект и FQN формы, сценарий, выбранный архетип и его обоснование.
Для элементов перечислить точные имена, родителя, dataPath, тип данных,
редактируемость и назначение. Для действий — команду, событие, метод, модуль,
контекст исполнения и подтверждённую связь. Неизвестное назвать явно.

Каждое предлагаемое изменение адресовать владельцу: FQN/элемент/свойство,
текущее и предлагаемое значение, причина и проверяемый результат по критерию.
Если текущая композиция подходит сценарию, вернуть обоснованное сохранение
структуры; шаблон сам по себе не создаёт работу на изменение.

Например, карточка справочника с основной группой и двумя полями не требует
второй колонки. Путь к данным подтверждается моделью, фокус — кодом обработчика.
Чтение кода не подтверждает вызов события в клиенте: это отдельная проверка
поведения по критериям задачи.

## Навигация рабочего интерфейса

У каждой пользовательской подсистемы должен быть осмысленный графический элемент: подходящая штатная картинка или подготовленная общая картинка. Картинку выбирай по роли раздела и проверяй в работающем интерфейсе. Служебные разделы тестового движка и генератора кода не должны становиться основными разделами рабочего места. Исключай их из командного интерфейса, сохраняя сам движок и возможность запуска тестов. Изменяй фактически установленное расширение, а не одноимённую копию в другом проекте.
